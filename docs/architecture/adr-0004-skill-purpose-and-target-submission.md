## Context

### Problem Statement

ADR-0004 revision 2 accepts a broad exclusion of Target development-only instructions,
including project-specific skills, standalone roles and native instruction bodies.
Its Decisions 2/3 and rejected project-specific alternative do not first limit the
collection to assets owned by the CDD framework. The current standard consequently
says that skills used only to develop the project are all templates, which can absorb
project-owned assets into the CDD boundary.

The requested correction changes this accepted public constraint. It is not a spelling
repair, an implicit exception or acceptance inferred from local write authority.
In retained revision 2, preserved Proposed wording is historical: that revision's
Acceptance Record establishes the current effective Accepted decision. ADR-0003 cannot be cited alone to bypass ADR-0004's later
qualification.

### Current State

Source baseline: `cb4f26131ed0fe7711634a6f14a2b328013461cb`, branch `main`.
Root instructions, T0/T2, adapter/directory norms and several installed skills repeat
the broad purpose rule. They already distinguish local presence/use from Git contents,
preserve required originals and deny automatic untracking or deletion authority.

### Constraints

- Preserve ADR-0001/0002 renderer ownership, complete selected projections and input closure.
- Preserve ADR-0003's Source/Target distinction and required local inputs separate from Git candidates.
- Preserve ADR-0004 revision 2's exact Accepted original and acceptance history; revision 3 has separate Proposed status.
- Do not change a business project, its Git index/history, runtime loading, hook activation or project state.
- Do not install dependencies or make a maintenance toolkit a normal-use prerequisite.
- Do not put project-specific regression names, repair logs or acceptance-process records in reusable rules.

### Requirements

- Recognize CDD ownership from actual provenance, governing ownership and substantive
  delivery role before applying the CDD instruction-purpose rule.
- Keep project-owned assets subject to their own project rules, even when used to
  develop that project or packaged as skills/native roles.
- Keep complete authorized local CDD inputs usable while excluding framework assets
  from Target Git tracking, staging, commits and delivery/publication contents.
- Review shared/mixed ownership by substantive content and dependency role; leave
  unresolved ownership pending instead of assuming every development instruction is CDD.
- Treat prior tracking, migration authority and preservation as separate decisions.

## Decision

Subject to separate exact-scope acceptance:

1. **Ownership precedes purpose.** Identify the actual governed project and Source/Target
   role, then establish provenance, ownership and delivery role for each complete
   instruction package and its references. Confirmed CDD framework templates, full
   platform projections and exclusive framework support form the CDD asset collection.
   Apply the instruction-purpose rule within that collection, not to every instruction
   used during project development. Location, filename, schema and a declaration alone
   are insufficient evidence of ownership.

2. **Project assets retain project rules.** Project-owned skills, agents/roles, tools,
   configuration, documents, source, tests and QA/history are not CDD templates merely
   because they develop the project, contain developer instructions or use a native
   skill directory. Project governance and substantive delivery evidence establish
   their ownership and eligibility. CDD instructions reading a project asset do not
   change that asset's ownership.

3. **CDD identity survives tailoring.** Renaming, packaging or customizing a CDD
   framework template does not by itself turn it into a project-owned asset.
   Within confirmed CDD packages, classify the complete body, conditional branches,
   projections and required exclusive support. Inspect shared/mixed content per part;
   split confirmed CDD framework content/support from project-owned candidates before
   submission. Unresolved ownership/classification keeps only the affected action pending.

4. **Git separation preserves local use.** CDD framework assets and maintenance tools
   remain outside Target Git tracking, staging, commits and delivery/publication.
   They may remain inside or outside the project and be discovered, loaded, take
   effect and be used under existing authorization. Ignore rules must not be treated
   as runtime loading controls. Required inputs must remain complete at usable paths.
   Optional authorized maintenance operations remain allowed; ordinary template use
   must not require the maintenance toolkit, a lock, a live Source or a Source ADR reader.

5. **Keep the bounded CDD-related eligible set.** Minimal project-specific bindings
   and independent portable configuration can remain candidates under project rules
   when they contain/reconstruct neither CDD framework instruction bodies nor exclusive
   support. A native loader alone does not make a copied CDD role body independent
   configuration. This CDD-related restriction does not apply to independently
   established project-owned development skills or roles.

6. **Keep Source delivery distinct.** The designated CDD Source delivers its developer
   templates and complete projections as framework product assets. Local Source
   maintenance tools, fixtures, annotations and execution records remain outside that
   delivery. A Target copy does not gain Source authority. Storage location alone
   neither establishes ownership nor authorizes moving or deleting material.

7. **Keep migration and effect safeguards.** Ignore rules do not remove tracked/staged
   content or prevent forced addition or separate publication. Existing tracked CDD
   content requires the applicable governance gate and separate exact-path tracking-only
   migration authority, with actual local files, required references, customizations,
   recoverable before bytes and Git history preserved. Project-owned assets must not
   be proposed for CDD untracking solely because they support development. This
   successor supplies no Target migration, index, delete/move, commit or publication authority.

## Alternatives Considered

### Alternative 1: Keep purpose alone as the ownership boundary

- **Pros:** A uniform development-only label simplifies exclusion.
- **Cons:** Project-owned development capabilities are absorbed into CDD; explicit
  project ownership and delivery decisions are lost.
- **Rejection Reason:** Contradicts the requested project-asset boundary.

### Alternative 2: Exempt packages by names, paths or a project-specific allowlist

- **Pros:** Quickly protects a named project's current skills.
- **Cons:** Hard-codes a project exception, misses other owned assets and can permit
  renamed CDD copies to evade ownership review.
- **Rejection Reason:** Ownership must be substantive and general, not a filename whitelist.

### Alternative 3: Implement before accepting the changed decision

- **Pros:** Makes the current instructions appear corrected sooner.
- **Cons:** Conflicts with an Accepted predecessor and mistakes local write authority
  or passing tests for governance acceptance.
- **Rejection Reason:** Preserve the explicit reviewed-successor gate.

## Consequences

### Positive

Project assets retain their actual owners while reusable CDD assets stay outside Target
Git delivery. Complete ignored local inputs remain available and ordinary use remains
independent of maintenance tooling.

### Negative

Reviewers must establish provenance, ownership and delivery role rather than relying on
one development-purpose label. Shared/mixed ownership needs content-level evidence and
may require a reviewed split; a fresh clone may still need local CDD inputs provisioned.

### Neutral

No business behavior, native runtime schema, loading configuration, hook activation,
project Memory Bank, stage or release qualification is changed by this proposal.
