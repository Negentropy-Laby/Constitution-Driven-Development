and portable project-specific configuration, with separately reviewed business
and substantive project documents retaining their own submission rules.

## Context

### Problem Statement

A required local read does not by itself determine whether its original belongs
in a business project's Git history. Source base `4fb94bc3c8eb584e8b26c10c54295bdce79bced6`
required the reusable neutral inputs in Target Git; branch
`dbfda64e1ce1f510f13d685a146ca0830b135443` changed that direction to local-only.
This is a public governing-contract choice under `standards/notes-adr-sync.md`,
not a mere wording or file-location correction.

### Current State and Governing Evidence

The earlier instruction change was introduced by
`2d0b7ea1a304af56056ac62357946552a35fe319`, included in the stated base. That
instruction text explicitly denied ADR-acceptance authority. Neither its merge
nor this branch's implementation constitutes formal acceptance.

ADR-0001/0002 require directly usable complete installed adapters, required
neutral inputs, one Source, canonical projections and honest evidence. They do
not decide the Git eligibility of reusable neutral template/standard/workflow/
skill-testing originals in a Target. No Accepted opposite direction is identified;
the disposition is `adr-required`, not an invented architectural violation.

ADR-0002 acknowledges that its historical 21,741-byte Proposed D7/D8 acceptance
witness has not been recovered. Current retained Accepted files are different
revisions. This proposal preserves that history and limitation; it neither
reconstructs the missing witness nor ratifies those choices again.

### Constraints

- Preserve the user's requested local-only direction; do not restore the older
  Target tracking instruction as a workaround for the missing governance gate.
- Preserve existing Accepted ADR bytes, Source ownership, declared complete
  projection/input contracts and the distinction between hooks and maintenance.
- Keep ordinary authorized use offline-capable without a local maintenance
  reader, import lock or generator. Missing actual required inputs remain pending.
- Keep location separate from content selected for Git/publication. Do not move,
  delete or untrack files just because the boundary text has changed.
- Preserve project-owned documents/configuration, business evidence, current
  scoped authorizations and actual required local originals.

### Requirements

A consumer must review readable inputs and Git candidates as separate per-file
sets. Import/update write authority names exact changed paths and outputs;
neither reading eligibility nor update-write authority confers Git eligibility.
A fresh Target clone may require separate provisioning of local originals before
an affected CDD workflow can run. That cost must remain explicit.

## Decision

### Proposed Scope

Subject to the pending governance gate:

1. The Source library retains reusable CDD development templates, neutral
   standard/workflow/skill-testing originals and necessary template-use support
   in its own eligible submission set. Formal Source architectural decisions
   supporting that public contract are not classified as tool-only process reports.
2. A Target's business code, substantive project documents and real business
   acceptance/QA/history use its governing project submission rules.
3. Its CDD Git candidates contain only required installed platform adaptations
   and portable project-specific configuration. Policies, business hooks and
   legal notices remain eligible when their actual role falls within those
   adaptations/configuration or substantive project documents under existing
   project rules. Calling a reusable neutral original "required support" does
   not make it Git-eligible; a path, generic name or keyword is not decisive.
4. Reusable neutral template/standard/workflow/skill-testing originals remain
   required where consumed, but local-only for this proposed Target Git boundary.
   Instantiated project documents and actual project-specific customizations
   are not automatically classified as reusable neutral originals.
5. General root skill/agent Source mirrors and template-maintenance tools,
   metadata and actual process output stay outside Target Git/publication under
   their existing separate rules. Local presence alone is unrestricted.
6. Existing Accepted Source topology/transforms/modes, complete selected installed
   packages and neutral-use dependency closure are unchanged. This proposal
   does not redefine a renderer scope or make missing inputs acceptable.

### Architecture and Key Interfaces

```text
Designated Source originals -> approved update paths -> installed platform files
                         \-> required neutral originals -> local-use input set
Business/substantive project files + required adaptations/config -> Git candidates
Required local-use input set does not grant Git membership or write authority.
```

The local-input allowlist names the complete actual readable closure for the
selected runtime/workflow. Git submission candidates name the separately eligible
content under Source/Target and project rules. Exact update-write paths name an
existing permission boundary for import/regeneration; they are neither list's
implicit union and add no new machine schema.

### Governance Gate and Implementation Limits

Independent authorized repairs/reviews and ordinary use of existing authorized

This proposal and its acceptance record belong to the owning Source governance
record. They add no Target runtime reader, configuration binding or required-input

## Alternatives Considered

### Alternative 1: Track all required reusable neutral originals in Target Git

- Pros: A clone carries these local inputs without separate provisioning.
- Cons: Conflates a business delivery set with reusable Source-owned inputs and
  duplicates the template library into project histories.
- Rejection Reason: The user explicitly chose local-only for these reusable
  inputs. The older direction also lacks an identified Accepted scope and is
  not restored to bypass the current `adr-required` gate.

### Alternative 2: Use one input set as automatic Git and update-write authority

- Pros: Fewer lists to inspect.
- Cons: A required read could authorize unwanted tracking or overwrite an
  unrelated project file; ignored placement would be mistaken for permission.
- Rejection Reason: Existing scope/ownership/evidence rules separate these
  effects. This proposal keeps the two sets and named write authority explicit.

### Alternative 3: Remove reusable originals from the local project entirely

- Pros: Fewer local copies.
- Cons: Breaks real consumers and offline work; location is not Source authority
  or Git eligibility, and the boundary supplies no deletion/move authority.
- Rejection Reason: Preserve actual required local originals and project history.

## Consequences

### Positive

Business Git contents and reusable Source input ownership can be reviewed
independently. Project-specific adaptations and evidence remain attributable,
and maintenance artifacts do not become normal-use prerequisites.

### Negative

A fresh Target clone can be incomplete for CDD use until its required neutral
originals are provisioned separately. Reviewers must maintain a complete local
input closure alongside the independently eligible Git set; installed files
alone do not prove current Source freshness or workflow execution.

### Neutral

No business runtime behavior, hook activation, Memory Bank initialization,
project law acceptance, stage progression or release qualification changes.

## Migration Plan

1. Read-only inventory the legacy Target's exact tracked reusable neutral inputs,
   required local-use closure and separately eligible project/platform candidates.
   Distinguish substantive project instances/customizations from reusable originals.
2. Preserve recoverable current before bytes, local originals and Git history.
   Record boundary reconciliation as pending; older tracking is not automatically
   grandfathered as compliant or judged against a newly Accepted direction.
3. Close this proposal's governance gate with exact-scope acceptance or a valid
   separately authorized existing-governance exception identifying authority,
   paths/effects, risks and duration. This draft grants none.
4. Obtain separate explicit project migration authority for the exact paths,
   tracking-only index effects, needed precise ignore changes and reference review.
   The new boundary text, a required read or a generic update approval grants no
   automatic untracking, deletion, relocation, commit or publication authority.
5. Under that scope remove only approved reusable neutral originals from Git
   tracking while leaving their actual local files and required dependency closure
   intact. Review actual index/diff, project customizations and retained history.
6. Commit/publication and any subsequent project state change require their own
   applicable authority and gates. No actual migration is performed by this ADR.

Rollback requires its own exact-scope authority and retained bytes; no reset,
cleanup, history rewrite or automatic re-tracking is authorized here.
